# PDKI Patent Analysis — Session Notes (29 March 2026)

## Overview

This session designed and built the **Patent Analysis** feature — a web-based, user-controlled interface for searching the Indonesian patent registry (PDKI) against a given Google Patent. It is built on top of the existing `pdki_pipeline.py` logic but gives the user full control over search terms and batches.

---

## Background: Existing PDKI Pipeline

Before this session, the only way to run PDKI searches was `PDKI/pdki_pipeline.py` — a CLI script that ran the full 10-step pipeline automatically end-to-end:

1. Fetch Google Patent metadata
2. AI (Haiku) generates search plan
3. Build batches from plan
4. Run Round 1 PDKI searches
5. Flag zero-hit batches
6. AI reflection for zero-hit alternatives
7. Run Round 2 PDKI searches
8. Merge + deduplicate results
9. Fetch detail pages
10. Save to JSON

The new web feature replaces the automated orchestration with a user-driven dashboard.

---

## What Was Built

### 1. Database — `utils/analysis_db.py`

A new SQLite database class `AnalysisDB` with three tables:

**`patent_analyses`**
Stores one record per Google Patent ID analysis. Fields: `id` (UUID), `google_patent_id`, `patent_data` (JSON — title, abstract, inventors, assignees, claims), `search_plan` (JSON — flat list of `{term, field}` items), `status` (`extracting` | `ready` | `error`), `error_message`, `created_at`, `updated_at`.

**`search_batches`**
Stores one record per batch run. Fields: `id` (UUID), `analysis_id` (FK), `batch_config` (JSON — searches + pagination), `status` (`pending` | `running` | `completed` | `failed`), `hit_count`, `error_message`, `created_at`, `completed_at`.

**`pdki_results`**
Stores deduplicated PDKI patent results. Fields: `id` (UUID), `analysis_id` (FK), `url`, `text`, `detail` (JSON — from detail extractor), `found_by` (JSON array of tags), `category` (NULL | `relevant` | `not_relevant` | `uncertain`), `created_at`. Unique constraint on `(analysis_id, url)` — deduplication key. On collision, `found_by` tags are merged.

### 2. Backend API Routes — `web_interface/backend/web_api.py`

Nine new routes added to the existing FastAPI app:

| Method | Route | Purpose |
|--------|-------|---------|
| POST | `/api/v1/analysis` | Create new analysis, start extraction background task |
| GET | `/api/v1/analysis` | List all analyses with result counts |
| GET | `/api/v1/analysis/{id}` | Get single analysis detail |
| PATCH | `/api/v1/analysis/{id}/search-plan` | Save user-edited search plan |
| POST | `/api/v1/analysis/{id}/batches` | Create and run a new search batch |
| GET | `/api/v1/analysis/{id}/batches` | List all batches for an analysis |
| GET | `/api/v1/analysis/{id}/batches/{batch_id}` | Poll a single batch status |
| GET | `/api/v1/analysis/{id}/results` | Get all deduplicated results |
| GET | `/api/v1/analysis/{id}/stats` | Get stats (total, analyzed, unanalyzed, by category) |

Two background tasks:

**`run_extraction_job(analysis_id, google_patent_id)`**
- Selenium fetches Google Patent metadata via `google_patents_clean_extractor`
- AI (Haiku) generates search plan via `ai_plan_searches` from `pdki_pipeline`
- Converts AI plan (nested `title_keywords`, `assignees`, `inventors`) to flat `[{term, field}]`
- Saves to DB with status `ready`

**`run_batch_job(analysis_id, batch_id, searches, pagination)`**
- Converts `[{judul, nama_inventor, nama_pemegang}]` rows to PDKI batch format
- Opens PDKI in Selenium, sets category to Paten, sets pagination
- Runs each search row sequentially using `fill_advanced_search` + `click_terapkan` + `extract_links`
- Deduplicates collected links by URL, merging tags
- Fetches detail page for each unique URL via `PDKI_detail_extractor`
- Upserts results into `pdki_results` table

Helper `_convert_to_pdki_batches(searches)`:
- Each row maps directly to `fill_advanced_search(driver, judul=..., nama_inventor=..., nama_pemegang=...)`
- Generates a readable `_tag` like `"title:valbenazine + assignee:Neurocrine"`
- PDKI filters by all filled fields simultaneously (AND logic) — more precise than single-field searches

Helper `_set_pagination(driver, n)`:
- Generic version of `set_pagination_100` — supports 10, 50, or 100

### 3. Frontend — `web_interface/frontend/index.html`

Added a **"Patent Analysis"** tab to the existing interface using **Vue.js 3 via CDN** (no build tooling). The Vue app is mounted on `#patentAnalysisApp` and exposed as `window.patentAnalysisApp` so the existing `TabManager` can trigger `loadAnalyses()` on tab switch.

Container `max-width` widened from 800px to 1100px to accommodate the dashboard layout.

**Three views:**

**List view** — shows all patent analyses as cards. Each card displays: Google Patent ID, patent title, last updated date, total results extracted. Includes a "+ New Analysis" button.

**Create view** — user inputs a Google Patent ID and clicks Extract. The backend starts the extraction + AI planning job in the background. The UI polls every 3 seconds until status is `ready`, then automatically navigates to the dashboard.

**Dashboard view** — the main working area for an analysis:

- *Source Patent* (collapsible) — title, abstract, inventors, assignees from Google Patents
- *Search Plan* (collapsible, editable) — table of `{term, field}` items generated by AI. User can add, edit, remove rows and save. Field options: Title, Inventor, Assignee.
- *Run New Batch Search* — table where each row is one PDKI search submission with three dropdowns (Title / Writer / Assignee). Dropdown options are populated from the saved search plan terms for that field. Multiple rows can be combined in one batch — each row runs as a separate sequential search. One pagination setting (10 / 50 / 100) applies to the whole batch.
- *Batch History* — table showing all past batches with status, search terms used (as colored pills), hit count, and timestamps.
- *Stats bar* — six boxes: Total Extracted, Analyzed, Unanalyzed, Relevant, Not Relevant, Uncertain.
- *Results table* — all deduplicated PDKI patents with title (linked to PDKI URL), status, found-by tags, and category.

## Key Design Decisions

**One analysis per Google Patent ID** — each analysis is independent, lives indefinitely, and can always accept new search batches. There is no "done" state.

**Search plan as flat list** — the AI plan is stored as `[{term, field}]` which maps cleanly to dropdown options in the UI and is editable by the user.

**Batch searches are multi-field** — each search row in the batch can fill title, inventor, and/or assignee simultaneously. PDKI applies AND logic across filled fields, making combined searches more precise than single-field searches.

**Deduplication by URL** — results are deduplicated at the database level via `UNIQUE(analysis_id, url)`. When a URL appears in multiple batches, the `found_by` tags are merged rather than creating duplicate rows. This means the user can add as many batches as they want and the results table always reflects unique patents only.

**Sequential search within a batch** — all search rows in a batch run one at a time on a single Chrome instance. This avoids Chrome profile conflicts and memory issues.

**Lazy imports for Selenium** — all `undetected_chromedriver` and PDKI module imports are inside the background task functions, not at module level. This prevents startup failures if Chrome is unavailable.

cd /app/patent_pipeline/web_interface/backend
uvicorn web_api:app --host 0.0.0.0 --port 8000
